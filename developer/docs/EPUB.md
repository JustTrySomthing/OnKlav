# EPUB chapters, TOC and text reflow (working source)

`epub::{info,chapter,search}` and `epub_ui::reader(title,input,private_blob_id)`
use `storage.private` through the production Rust broker. Import a user-selected
book with `blobs::import` (also `files.external`), then pass its immutable private
handle to the shared reader. Guest code supplies no paths or archive URLs.

The supported profile is **offline text reflow for EPUB2/3**, not full visual
EPUB conformance. It follows the package spine, chooses the first container
rootfile, reads EPUB3 navigation TOCs or EPUB2 NCX, resolves local fragments,
and uses the shared themed native text screen. See the primary format references:
[EPUB3.3](https://www.w3.org/TR/epub-33/) and
[Reading Systems3.3](https://www.w3.org/TR/epub-rs-33/).

## Services

| Service | Input | Result |
| --- | --- | --- |
| `epub.info` | `id` | Title, immutable source revision, ordered chapters, TOC targets, profile |
| `epub.chapter` | `id,chapter` | Chapter text, title, UTF-8 anchor offsets and revision |
| `epub.search` | `id,query,chapter,offset` | Up to40 literal case-sensitive matches and a continuation cursor |

Search crosses chapter boundaries, preserves Unicode byte ranges and does not
execute regex or fetch external content. The shared screen offers20-row TOC
pages, whole-book search, exact match/fragment jumps, previous/next chapter and
page controls. Chapters wrap using the user's host font/theme settings. Chapter
and page positions are app-private and revision checked. Unsaved positions remain
visible; retry requires explicit review before replacing a conflicting bookmark,
and leaving an unsaved chapter asks for confirmation.

## Deliberate limits

- ZIP input at most20MiB,1024 entries,32MiB total declared expansion and8MiB per
  entry. XML resources are at most1MiB. No extraction to filesystem paths occurs.
- Up to200 spine chapters and200 TOC entries; combined returned metadata at most
  64000 JSON bytes. Each reflowed chapter is at most120000 UTF-8 bytes and its
  anchor map at most16384 JSON bytes, keeping the guest's450000-byte state budget.
- Search returns40 matches per call and examines at most8 million text bytes in
  one batch; continuation resumes at a Unicode boundary in the next batch.
- UTF-8 XML; bounded depth64,100000 events and64 attributes per element. Internal
  DTD/entity declarations are refused. External doctype identifiers are never
  fetched/resolved; only built-in/numeric and a small explicit typography entity
  set is decoded. Unknown entities fail clearly.
- Duplicate entries/spine paths, symlinks, archive-root escape, remote manifest/TOC references,
  missing TOCs/resources and malformed XML are rejected. Unsupported chapter
  content reports an error and keeps the private source unchanged.
- DRM/encryption and font-obfuscation packages, fixed layout, scripts, iframe,
  object and embed content are unsupported. No WebView, JavaScript or network is
  used. Author CSS/fonts are not loaded; text reflows in the user's host style.
- Images appear as explicit alt-text placeholders, not rendered images. SVG/math
  is labelled as illustration/formula text, without visual layout fidelity.
  This profile is suitable for text books, not illustrated/fixed-layout editions.

`reading_ui` supplies per-chapter page bookmarks in `reading_positions_v1`;
`epub_ui` stores the active chapter in `epub_books_v1`. Reserve these collections
for the components. A different immutable blob revision cannot reuse old page
positions. The public `reading_ui::go_to` validates parent-owned fragment/search
jumps and uses the normal position transaction; it does not create a host action.

The executable source example is `developer/examples/epub-reader`. Its synthetic
fixture is generated by `scripts/make_epub_fixture.py`. Verification signs only a
disposable guest and tests the real Rust broker, without creating an APK or
updating a bundled signed app. Current evidence is `docs/epub-verification.json`.
Actual Android rendering, device accessibility/layout and large-book performance
remain qualification work. PDF is the separate next chunk30.
